## 2025-06-10 - IDOR in nested resources using findUniqueOrThrow
**Vulnerability:** A nested resource update endpoint (`/api/my-tasks/[id]/checklist/[itemId]`) was using `prisma.findUniqueOrThrow` to fetch the item relying solely on the primary key (`itemId`). This created an Insecure Direct Object Reference (IDOR) because it failed to enforce the relationship bounds (ensuring the `itemId` actually belonged to the `taskId` from the URL) and it bypassed the tenant and assignee authorization checks.
**Learning:** Even if a parent resource authorization is checked elsewhere, the query for any child resource must explicitly enforce its relationship to the authorized parent entity. Querying merely by the primary key is insecure in multi-tenant or scoped environments. Using `findUniqueOrThrow` with invalid/missing bounds leads to unhandled exceptions (HTTP 500) rather than standard 404s.
**Prevention:** For any nested or scoped resource modification, replace `findUniqueOrThrow` relying only on primary keys with `findFirst`. Include explicit relationship filters (e.g. `task_id: id`) and authorization bounds (e.g. `task.company_id` and `task.assigned_to`) within the `where` clause, and safely handle the potential `null` result with a 404 response.
