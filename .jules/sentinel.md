## 2024-06-19 - [IDOR in Nested Checklist Items]
**Vulnerability:** Endpoints handling nested resources (e.g., `/api/tasks/[id]/items/[itemId]`) allowed updating checklist items by referencing only their primary key (`itemId`), without verifying if the item actually belonged to the specified task and if the user had authorization for that task/company. This meant a user could pass a valid `itemId` belonging to a different company and update it, bypassing tenant isolation.
**Learning:** `findUniqueOrThrow` using only a primary key is insufficient for nested resources because it doesn't enforce relationship bounds or tenant isolation. Also, relying solely on the parent resource's route parameter for authorization without linking it to the child resource query is a common source of IDOR.
**Prevention:** Always use `findFirst` to enforce relationship constraints in the query itself when accessing nested resources. Verify the item ID, its relationship to the parent task ID, and the parent task's tenant boundaries (`company_id`, `assigned_to`) in a single query before performing operations. Return a generic 404 response if the item is not found or not authorized.
