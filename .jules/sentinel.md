
## 2024-05-13 - Enforce Parent-Child Relationship for Nested Resources to Prevent IDOR
**Vulnerability:** A missing authorization check in the `/api/my-tasks/[id]/checklist/[itemId]` endpoint allowed users to modify checklist items belonging to tasks they were not assigned to, simply by manipulating the `itemId` parameter. The endpoint queried the checklist item solely by its `id` using `findUniqueOrThrow`.
**Learning:** For nested resources (like items within a task), it is insufficient to only validate the `id` of the child resource or the ownership of the parent resource independently. The database query itself must explicitly enforce the relationship between the child (`itemId`) and the parent (`id`), and subsequently, the parent's relationship to the user (`company_id` and `assigned_to`).
**Prevention:** Use `findFirstOrThrow` (or `findFirst`) instead of `findUnique` to allow querying by multiple fields. Construct the `where` clause to include both the child resource `id`, the parent resource `id` (e.g., `task_id`), and any tenant/ownership scopes on the parent relation (e.g., `task: { company_id: auth.employee.company_id, assigned_to: auth.employee.id }`).
