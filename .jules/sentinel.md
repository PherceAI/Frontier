
## 2026-06-06 - [HIGH] Fix IDOR in config areas API
**Vulnerability:** In `frontend/src/app/api/config/areas/[id]/route.ts`, the `PATCH` and `DELETE` endpoints used `prisma.operationalArea.update` by providing only the `id` from the URL parameters. Because `update` requires unique identifiers and cannot natively include arbitrary non-unique fields like `company_id` in its `where` clause out-of-the-box in the same query without a custom compound unique key, the application did not verify tenant isolation. This created an Insecure Direct Object Reference (IDOR) where any admin could modify or delete operational areas belonging to other companies.
**Learning:** When using Prisma, mutation operations (`update`, `delete`) natively restrict their `where` clause to unique fields. A common mistake is to only filter by the ID without manually ensuring the resource belongs to the current tenant (`company_id`), leading to privilege escalation or IDOR across tenants.
**Prevention:** Always perform a preliminary read check using `prisma.findFirst` with the tenant filter (`company_id: user.company_id`) before executing any mutation methods. If the resource isn't found, return a `404 Not Found` response. Alternatively, if appropriate for the schema, configure composite unique keys that include the tenant ID to enforce isolation directly in the mutation query.
