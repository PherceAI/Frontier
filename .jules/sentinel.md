
## 2024-06-05 - Insecure Direct Object Reference (IDOR) & Unhandled 500 Exceptions in Nested Resources
**Vulnerability:** Employee task endpoints (like `/api/my-tasks/[id]/checklist/[itemId]`, `/api/my-tasks/[id]/complete`, and `/api/my-tasks/[id]/start`) were using `prisma.findUniqueOrThrow` querying solely by the resource ID or lacked `company_id` filters, while also executing database `update` mutations directly based on parameters. Additionally, using `findUniqueOrThrow` for missing items caused uncaught exceptions (HTTP 500) rather than a controlled HTTP 404 response.
**Learning:** In a multi-tenant or multi-user environment, querying nested resources exclusively by their ID fails to enforce relational boundaries (e.g., verifying a checklist item actually belongs to the given task, and that task is assigned to the authenticated user). This allows an attacker to manipulate items belonging to other users or companies by substituting IDs.
**Prevention:** To prevent IDOR and 500 errors, use `prisma.findFirst` instead of `findUniqueOrThrow` to enforce relationship bounds (e.g., `company_id`, `assigned_to`, and parent IDs) in the `where` clause before performing any mutation. If `findFirst` returns null, return a sanitized JSON 404 response instead of throwing a generic server error.
