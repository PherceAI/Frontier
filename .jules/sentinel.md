
## 2024-06-07 - Insecure Direct Object Reference (IDOR) via Prisma Mutations
**Vulnerability:** The API endpoint for configuring operational areas (`PATCH` and `DELETE` at `/api/config/areas/[id]`) executed `prisma.operationalArea.update` directly using an unverified user-supplied `id`. Because Prisma's `update` and `delete` functions require the condition to be uniquely identifying, adding non-unique parameters like `company_id` to the `where` clause is not permitted by Prisma's generated type system. Consequently, the endpoint implicitly trusted that any requested `id` belonged to the authenticated admin's `company_id`.
**Learning:** In multi-tenant environments using Prisma, one cannot simply add tenant filters directly to `update`/`delete` mutations if the `where` clause relies strictly on primary keys. The absence of a preliminary verification step resulted in an IDOR where an authenticated user could maliciously alter or delete resources of other tenants by simply knowing or guessing the resource's UUID. Attempting to use `findUniqueOrThrow` with only the `id` still failed to enforce tenant boundaries, while using it with multiple arguments caused compiler errors.
**Prevention:** Always enforce tenant isolation and ownership prior to performing mutations. When updating or deleting Prisma records based on an `id`, first perform a `prisma.findFirst` query that explicitly filters by both the target `id` and the context `company_id`. To avoid unhandled HTTP 500 exception errors, use `findFirst` followed by manually returning a 404 response instead of relying on `findFirstOrThrow` or `findUniqueOrThrow`.
