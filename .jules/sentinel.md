## 2024-04-27 - [Prevent IDOR in Nested Task Resources]
**Vulnerability:** Several endpoints like `/api/operations/tasks/[taskId]/items/[itemId]/route.ts`, `/api/my-tasks/[id]/checklist/[itemId]/route.ts`, and `/api/operations/tasks/[taskId]/route.ts` used `findUniqueOrThrow` or `findFirstOrThrow` solely based on the resource ID (e.g., `id: itemId` or `id: taskId`), failing to enforce tenant isolation and ownership rules. This could allow an authenticated user to modify task or checklist item details belonging to a different company or employee by directly manipulating the IDs in the request URL.
**Learning:** In a multi-tenant system using Prisma, nested resources must explicitly enforce relationships (e.g., verifying `itemId` belongs to `taskId`) AND tenant context (e.g., `company_id: auth.employee.company_id`) in all `where` clauses before mutation. When updating nested entities, querying them via relationships back to the tenant ensures proper scoping.
**Prevention:** Always use `findFirstOrThrow` to validate ownership and context parameters (like `company_id` or `assigned_to` from the session) alongside resource IDs before performing `update` or `delete` actions, especially for multi-tenant data structures.
