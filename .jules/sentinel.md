## 2024-06-16 - IDOR in Nested Resources
**Vulnerability:** Insecure Direct Object Reference (IDOR) vulnerabilities existed in the task update endpoint and task checklist item update endpoint. The endpoints used `findFirstOrThrow` or `findUniqueOrThrow` to locate objects strictly by their resource ID (e.g., `taskId` or `itemId`) without enforcing tenant isolation (`company_id`), ownership boundaries (`assigned_to`), or hierarchical structure (verifying that `itemId` belongs to `taskId`).
**Learning:** This architectural gap allowed any authenticated user to potentially modify another user's or company's tasks/checklists just by enumerating IDs, and caused HTTP 500 unhandled exceptions when using `OrThrow` on invalid IDs.
**Prevention:** To prevent IDOR in multi-tenant and nested resource operations, always use `findFirst` to enforce tenant isolation (`company_id`), explicit ownership (`assigned_to`), and parent-child relationships (e.g., verifying `itemId` belongs to `taskId`) within the database query itself. Return an explicit 404 response instead of throwing an unhandled HTTP 500 error.
